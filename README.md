# 尋路演算法視覺化比較平台 — 網站規格書

**英文名稱：** Pathfinding Algorithm Visualizer
**專案類型：** 互動式 Web App
**開發方式：** Vibe Coding（AI 輔助開發）
**部署方式：** GitHub Pages
**最終交付：** 單一 `index.html` 檔案

---

## 一、專案概述

### 1.1 專案動機

在學習演算法時，僅透過文字、虛擬碼或靜態圖片，往往難以直觀理解不同演算法的執行過程及其差異。

本專案希望透過互動式網頁，將 DFS、BFS、Dijkstra、A\* 四種尋路演算法的搜尋過程視覺化，讓使用者能夠在完全相同的地圖條件下，同時觀察不同演算法如何探索節點、尋找終點，並比較最終路徑與搜尋效率。

### 1.2 專案目標

1. 透過動畫呈現四種尋路演算法逐步探索地圖的過程。
2. 提供相同地圖環境，公平比較不同演算法的搜尋行為。
3. 讓使用者自由調整地圖大小、障礙物、起點與終點。
4. 提供播放控制功能，方便觀察演算法每一步的執行狀態。
5. 透過統計數據及圖表比較不同演算法的執行結果。
6. 建立直觀、美觀且具有教學價值的互動網站。

### 1.3 目標使用者

- 正在學習資料結構與演算法的學生。
- 想了解不同尋路演算法差異的使用者。
- 需要展示尋路演算法執行過程的教學者。

## 二、網站介面設計

### 2.1 整體視覺風格

參考使用者提供的四宮格演算法視覺化圖片，採用深色科技風格。

設計原則：

- 以黑色、深灰色作為主要背景。
- 使用卡片式設計區分不同功能區域。
- 使用鮮明顏色表示地圖中的不同狀態。
- 地圖格子應排列整齊、間距一致。
- 使用簡潔的文字、按鈕及圖示。
- 適度使用動畫與互動回饋。
- 避免過度裝飾影響演算法視覺化的清晰度。

### 2.2 網站區域

網站由三個主要區域組成。

**區域 A：上方控制面板**

包含：

- 網站名稱。
- 地圖大小選單。
- 障礙物配置選單。
- 起點、終點設定選單。
- 重新生成地圖按鈕。
- 清空障礙物按鈕。
- 手動編輯工具。
- 播放控制按鈕。
- 動畫速度調整。
- 共用播放時間軸。

**區域 B：四宮格演算法視覺化**

桌面版採用 2×2 排列：

| 左上                      | 右上                        |
| ----------------------- | ------------------------- |
| Depth-First Search（DFS） | Breadth-First Search（BFS） |
| A\* Search（A-Star）      | Dijkstra's Algorithm      |

每個區域包含：

- 演算法名稱。
- 地圖格子。
- 演算法執行狀態。
- 已探索節點數。
- 目前執行步數。
- 最終路徑長度。

四張地圖必須使用相同的大小、障礙物、起點及終點。

**區域 C：演算法比較結果**

包含：

- 四種演算法的比較表格。
- 已探索節點數比較長條圖。
- 最終路徑長度比較。
- 實際演算法計算時間。
- 各演算法簡短說明。

### 2.3 響應式設計

- 桌面螢幕：四張地圖以 2×2 排列。
- 窄螢幕及手機：四張地圖改為單欄排列。
- 控制面板在窄螢幕下允許自動換行。
- 地圖應依照容器寬度縮放，維持正確的列數、欄數與格子比例。
- 地圖格子保持正方形，不得因響應式排版而變形。

## 三、地圖設定功能

### 3.1 地圖大小

提供四種選項：

| 選項  | 列數 × 欄數      |
| --- | ------------ |
| 小地圖 | 10 × 20      |
| 中地圖 | 20 × 35      |
| 大地圖 | 30 × 45      |
| 隨機  | 隨機選擇以上三種尺寸之一 |

使用者切換地圖大小後，重新建立地圖並清除原本的搜尋結果。

預設使用中地圖。

### 3.2 障礙物配置

提供四種選項：

| 選項      | 障礙物比例   |
| ------- | ------- |
| 隨機（高密度） | 40%     |
| 隨機（中密度） | 25%     |
| 隨機（低密度） | 10%     |
| 手動      | 使用者自行編輯 |

障礙物使用深灰色表示，不能通行。

隨機配置規則：

1. 根據目前地圖尺寸與密度，隨機選擇障礙物格子。
2. 起點與終點不可被設定為障礙物。
3. 隨機地圖必須至少存在一條從起點到終點的可行路徑。
4. 使用 BFS 或等效方式檢查可達性。
5. 若不可達，重新生成障礙物。
6. 最多嘗試 100 次。
7. 若仍無法產生可行地圖，顯示失敗提示，提供重新生成按鈕，不得無限迴圈。
8. 若生成失敗，保留最後一張成功建立的有效地圖；若尚無有效地圖，則保留無障礙物的可用地圖。

障礙物密度為目標比例，因格子數取整可能存在少量差異。

### 3.3 手動障礙物設定

當使用者切換至「手動」模式：

1. 清除目前地圖上的所有障礙物。
2. 保留原本的起點與終點。
3. 啟用地圖編輯功能。
4. 使用者可以點擊或拖曳格子新增障礙物。
5. 再次點擊障礙物可以將其移除。
6. 不允許將起點或終點設定為障礙物。
7. 在任一演算法地圖上進行編輯，其他三張地圖必須立即同步更新。

提供以下編輯工具：

- 畫障礙物。
- 擦除障礙物。
- 設定起點。
- 設定終點。

手動編輯完成後，不強制要求地圖一定存在可行路徑。

如果起點與終點無法連通，仍允許執行演算法，最後顯示「無法抵達」。

### 3.4 起點與終點設定

提供兩種模式：

**隨機模式**

- 起點與終點隨機產生。
- 兩者不得位於相同格子。
- 不得位於障礙物格子。
- 不限制必須位於地圖邊緣。
- 隨機生成地圖時，應確保兩者可連通。

**手動模式**

- 使用者選擇「設定起點」或「設定終點」工具。
- 點擊地圖格子指定位置。
- 起點與終點不得重疊。
- 若選取的格子原本是障礙物，先移除該障礙物，再設定起點或終點。
- 四張地圖立即同步更新。
- 手動修改後允許出現無法抵達的情況。

### 3.5 地圖同步規則

四個演算法必須共用同一份地圖資料。

所有地圖修改操作，包括：

- 修改地圖大小。
- 修改障礙物配置。
- 新增或刪除障礙物。
- 修改起點。
- 修改終點。
- 重新生成地圖。

都必須同步反映在四張地圖上。

但每個演算法的搜尋狀態必須獨立保存，不得互相影響。

## 四、尋路演算法規格

### 4.1 支援演算法

網站固定同時顯示以下四種演算法：

1. Depth-First Search（DFS）
2. Breadth-First Search（BFS）
3. Dijkstra's Algorithm
4. A\* Search（A-Star）

不提供演算法勾選或切換功能。

### 4.2 共通規則

四種演算法統一使用：

- 相同地圖。
- 相同起點與終點。
- 相同障礙物配置。
- 上下左右四方向移動。
- 不允許斜向移動。
- 每次移動成本固定為 1。
- 探索方向優先順序為：上 → 右 → 下 → 左。
- 不允許移動至地圖外或障礙物。
- 起點到終點的路徑長度以移動步數計算。

當多個候選節點具有相同優先權時，使用固定且可重現的順序處理，確保同一張地圖的演算法結果具有一致性。

### 4.3 DFS

- 使用 Stack（堆疊）實作。
- 優先沿著一條路徑深入探索。
- 無法繼續時進行回溯。
- 依照上 → 右 → 下 → 左的方向優先順序探索。
- 使用適當的鄰居入堆疊順序，確保實際探索順序符合要求。
- 使用 visited 集合避免重複探索。
- 記錄 parent 以重建找到的路徑。
- 不保證找到最短路徑。

### 4.4 BFS

- 使用 Queue（佇列）實作。
- 依照上 → 右 → 下 → 左的順序檢查鄰居。
- 按照距離起點的步數逐層探索。
- 使用 visited 集合避免重複加入。
- 記錄 parent 以重建路徑。
- 在目前無權重地圖中保證找到最短路徑。

### 4.5 Dijkstra

- 使用 Min-Priority Queue 實作。
- 每次選擇目前已知累積成本最低的節點進行擴展。
- 使用 dist 陣列記錄起點到各節點的最低已知成本。
- 當找到更低成本的路徑時，更新距離及 parent。
- 使用固定順序處理成本相同的候選節點。
- 在目前所有移動成本皆為 1 的地圖中，保證找到最短路徑。

### 4.6 A\*

- 使用 Min-Priority Queue 實作。
- 使用以下評估函數：

  f(n) = g(n) + h(n)

其中：

- g(n)：從起點到目前節點的已知最低成本。
- h(n)：從目前節點到終點的估計成本。
- f(n)：預估經過目前節點抵達終點的總成本。

啟發式函數固定使用 Manhattan Distance：

h(n) = |row(n) - row(end)| + |col(n) - col(end)|

- 每次優先擴展 f 值最低的節點。
- f 值相同時使用固定規則決定順序。
- 記錄 parent 以重建最終路徑。
- 在目前四方向、單位移動成本的設定下，保證找到最短路徑。

### 4.7 演算法終止條件

以下情況結束搜尋：

1. 從待探索集合取出的節點為終點，表示成功。
2. 待探索集合為空且尚未找到終點，表示無法抵達。

若成功：

- 停止探索。
- 根據 parent 重建最終路徑。
- 顯示黃色路徑。
- 更新最終統計。

若失敗：

- 停止探索。
- 顯示「無法抵達」。
- 不顯示黃色最終路徑。
- 保留已探索區域。

## 五、地圖視覺化規格

### 5.1 格子顏色

| 格子狀態    | 顏色     |
| ------- | ------ |
| 未探索、可通行 | 黑色或極深灰 |
| 障礙物     | 深灰色    |
| 已探索節點   | 藍色     |
| 最終路徑    | 黃色     |
| 起點      | 綠色     |
| 終點      | 紅色     |

起點與終點顏色具有最高顯示優先權，不得被搜尋動畫覆蓋。

### 5.2 搜尋動畫

- 每個演算法都必須逐步顯示節點探索過程。
- 新探索的節點由未探索顏色變為藍色。
- 不得直接跳到最終結果。
- 搜尋完成時，立即以黃色顯示完整最終路徑。
- 已探索但不屬於最終路徑的格子維持藍色。
- 障礙物不受搜尋動畫影響。

### 5.3 格子資訊

滑鼠懸停在格子上時，顯示：

- 格子座標（row, column）。
- 格子狀態。
- 若已探索，顯示該格在目前演算法中被擴展的步數。

座標從 (0, 0) 開始。

## 六、動畫播放控制

### 6.1 共用控制列

四個演算法使用同一組播放控制。

提供：

- 開始。
- 暫停。
- 繼續。
- 重置。
- 單步執行。
- 上一步。
- 動畫速度調整。
- 共用時間軸。

### 6.2 同步播放機制

四個演算法使用相同的播放節奏。

每個全域播放步驟：

- DFS 最多擴展一個節點。
- BFS 最多擴展一個節點。
- Dijkstra 最多擴展一個節點。
- A\* 最多擴展一個節點。

已完成的演算法不再擴展節點。

其他尚未完成的演算法繼續執行，直到四個演算法全部完成。

同步播放的目的是比較各演算法需要多少個節點擴展步驟，而非模擬實際 CPU 執行速度。

### 6.3 動畫速度

提供 1～10 級速度調整。

建議對應：

- 1 級：每秒 2 步。
- 5 級：每秒 20 步。
- 10 級：每秒 120 步。

中間級別可使用合理的漸進速度配置。

速度調整應立即生效，不需要重新開始動畫。

### 6.4 暫停與繼續

- 暫停後保留四張地圖的目前狀態。
- 繼續後從原本步驟接續播放。
- 不重新計算地圖。
- 不清除已探索節點。

### 6.5 單步執行

- 每次點擊「下一步」，四個演算法各最多擴展一個節點。
- 已完成的演算法保持原狀。
- 點擊「上一步」可回到前一個全域播放步驟。
- 允許從任意歷史步驟重新向前播放。

### 6.6 共用時間軸

- 提供一條可拖曳的進度時間軸。
- 時間軸代表全域節點擴展步數，而非實際秒數。
- 最大值為四個演算法中需要最多擴展步驟的數量。
- 拖曳時間軸時，四張地圖同步顯示對應歷史狀態。
- 若某演算法已在較早步驟完成，後續保持完成狀態。
- 使用者拖曳時間軸時，先暫停自動播放。
- 可以從拖曳後的位置繼續播放。

### 6.7 重置與重播

**重置：**

- 清除四個演算法的搜尋痕跡。
- 清除黃色最終路徑。
- 清除目前統計結果。
- 將播放步驟歸零。
- 保留原本地圖、障礙物、起點及終點。

**重播：**

- 搜尋全部完成後，可以直接重新播放相同的搜尋過程。
- 不重新生成地圖。
- 不改變演算法結果。

## 七、統計資訊與比較結果

### 7.1 每個演算法的資訊

每張地圖顯示：

- 演算法名稱。
- 目前執行狀態。
- 已探索節點數。
- 目前執行步數。
- 最終路徑長度。

執行狀態包含：

- 尚未開始。
- 搜尋中。
- 已暫停。
- 已找到終點。
- 無法抵達。

統計資訊在播放過程中即時更新。

### 7.2 探索節點數

統一採用以下定義：

「演算法從待探索集合取出一個有效節點，並正式擴展該節點」計為一次探索。

- 起點被擴展時也計入。
- 終點被取出並確認時也計入。
- 重複或過期的 Priority Queue 項目不計入。
- 單純加入待探索集合的節點不計入。

### 7.3 最終路徑長度

使用移動步數表示：

- 起點到相鄰格子為 1 步。
- 不包含起點本身。
- 若無法抵達，顯示「—」。

### 7.4 實際演算法計算時間

- 使用瀏覽器高精度計時工具測量演算法計算時間。
- 不包含動畫等待時間。
- 不包含使用者暫停時間。
- 不將動畫播放速度當作計算效能。
- 單位為毫秒（ms）。
- 計算時間為環境相關的參考數據，不應宣稱為嚴格的效能基準測試。

### 7.5 比較結果表格

四個演算法完成後，顯示：

| 演算法      | 探索節點數 | 路徑長度 | 計算時間 | 結果    |
| -------- | ----: | ---: | ---: | ----- |
| DFS      |  實際結果 | 實際結果 | 實際結果 | 成功／失敗 |
| BFS      |  實際結果 | 實際結果 | 實際結果 | 成功／失敗 |
| Dijkstra |  實際結果 | 實際結果 | 實際結果 | 成功／失敗 |
| A\*      |  實際結果 | 實際結果 | 實際結果 | 成功／失敗 |

所有數據必須來自實際演算法運算，不得使用固定或模擬數字。

### 7.6 比較圖表

至少提供：

1. 四種演算法的探索節點數長條圖。
2. 四種演算法的最終路徑長度比較。

無法抵達的演算法應清楚標記，不得將失敗路徑長度誤表示為 0。

### 7.7 演算法簡介

比較區域附上四種演算法的簡短說明：

- DFS：優先深入探索，不保證最短路徑。
- BFS：逐層探索，在無權重地圖中保證最短路徑。
- Dijkstra：優先探索累積成本最低的節點。
- A\*：利用已走成本與終點距離估計引導搜尋。

## 八、使用者操作流程

### 8.1 首次開啟網站

1. 自動建立中地圖（20×35）。
2. 預設使用中密度障礙物（25%）。
3. 隨機產生起點與終點。
4. 確保至少存在一條可行路徑。
5. 四張地圖顯示相同的初始配置。
6. 所有演算法狀態為「尚未開始」。

### 8.2 修改地圖

1. 使用者選擇地圖大小。
2. 選擇障礙物密度或手動模式。
3. 選擇隨機或手動設定起點、終點。
4. 四張地圖同步更新。
5. 原本的動畫與搜尋結果清除。

### 8.3 執行演算法

1. 點擊「開始」。
2. 四個演算法同步開始探索。
3. 藍色格子逐步增加。
4. 每個演算法完成後顯示黃色路徑或搜尋失敗。
5. 四個演算法全部結束後，顯示完整比較結果。

### 8.4 觀察與比較

使用者可以：

- 暫停動畫。
- 調整速度。
- 單步前進。
- 回到上一個步驟。
- 拖曳時間軸。
- 查看格子座標與探索順序。
- 比較探索節點數。
- 比較最終路徑長度。
- 查看實際計算時間。

## 九、狀態管理與特殊情況

### 9.1 修改地圖時

只要地圖內容發生變化：

- 立即停止動畫。
- 清除四個演算法的搜尋結果。
- 將播放步驟歸零。
- 清除舊的比較數據。
- 保留修改後的新地圖。

### 9.2 手動地圖無法抵達終點

- 允許正常執行四種演算法。
- 各演算法在待探索集合耗盡後停止。
- 顯示「無法抵達」。
- 保留藍色已探索區域。
- 不顯示黃色路徑。

### 9.3 隨機生成失敗

- 最多嘗試 100 次。
- 顯示清楚的錯誤提示。
- 提供重新生成操作。
- 不讓網頁陷入無限迴圈。
- 不讓四張地圖出現不一致狀態。

### 9.4 重複操作

- 連續點擊開始不得產生多個動畫計時器。
- 暫停後再次開始應正確繼續。
- 重置後可重新執行。
- 時間軸來回拖曳不得改變演算法原始結果。
- 已完成演算法不得重複增加探索節點數。

### 9.5 重新整理網頁

- 不需要保存上次的地圖。
- 每次重新開啟網頁，重新產生預設隨機地圖。
- 不需要使用者帳號或雲端資料庫。

## 十、技術規格

### 10.1 開發限制

最終作品必須整理成單一 `index.html`。

- HTML、CSS、JavaScript 全部包含於同一個檔案。
- 不依賴自行架設的後端。
- 不需要資料庫。
- 不需要 API Key。
- 不需要使用者登入。
- 不需要建置流程。
- 可直接部署至 GitHub Pages。

優先使用原生 JavaScript、CSS Grid、HTML Canvas 或 DOM 元素完成視覺化。

若使用第三方函式庫，必須確保 GitHub Pages 可正常載入，但應優先避免不必要的外部依賴。

### 10.2 建議程式架構

雖然程式碼位於單一 HTML 檔案中，仍應在 JavaScript 內保持清楚的邏輯分工：

1. 地圖資料與生成模組。
2. 地圖編輯與同步模組。
3. DFS 演算法模組。
4. BFS 演算法模組。
5. Dijkstra 演算法模組。
6. A\* 演算法模組。
7. 動畫播放與歷史狀態模組。
8. 地圖渲染模組。
9. 統計與比較圖表模組。
10. 使用者介面事件處理模組。

### 10.3 搜尋過程記錄

為了支援單步操作、上一個步驟及時間軸回放，建議：

- 演算法先完成搜尋計算。
- 記錄每個節點被正式擴展的順序。
- 記錄搜尋成功或失敗結果。
- 記錄最終路徑。
- 動畫依照記錄逐步播放。

各演算法必須有獨立的搜尋紀錄。

播放、暫停、重播及時間軸操作不得重新執行搜尋演算法。

### 10.4 效能要求

- 小、中、大地圖皆應可正常運作。
- 大地圖（30×45，共 1350 格）應保持操作流暢。
- 不得因快速播放而讓網頁長時間失去回應。
- 避免不必要的全畫面重繪。
- 使用適當的動畫更新機制。
- 避免大量重複計算與記憶體浪費。
